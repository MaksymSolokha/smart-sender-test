# Smart Sender — Webhooks (тестове завдання)

React 19 + TypeScript (strict) + MSW. Вхід, список вебхуків із пагінацією/пошуком і редагування.

## Запуск

```bash
pnpm install
pnpm dev        # http://localhost:5173
```

```bash
pnpm test       # Vitest: rotate / CSRF / схеми
pnpm typecheck  # tsc --noEmit
pnpm build
```

Потрібні Node 20+ і pnpm 10 (`corepack enable` або `npm i -g pnpm`). API повністю імітується MSW (Service Worker `public/mockServiceWorker.js`), бекенд не потрібен.

## Тестові облікові дані

- Email: `admin@example.com`
- Пароль: `password123`

Невірний пароль повертає 422 з помилкою на полі `password`.

## Стек

| Задача | Рішення |
| --- | --- |
| Збірка | Vite |

## Структура

```
src/
  api/            HTTP-клієнт і функції ендпоінтів (без React)
    httpClient.ts   CSRF, 419, 401 → rotate → повтор
    auth.ts         login + issue, revoke
    schemas.ts      zod-схеми відповідей і типи з них
    webhooks.ts, user.ts, types.ts, errors.ts
    httpClient.test.ts
  features/
    auth/         AuthProvider (стан сесії), RequireAuth, LoginPage
    webhooks/     запити (React Query), стан списку в URL, таблиця, форма і її zod-схема
  components/     layout і стани завантаження/помилки
  lib/            fingerprint, мапінг серверних помилок у форму
  mocks/          MSW: in-memory "БД", хендлери, setup для браузера і Node
```

Шари залежать в одному напрямку: `api` нічого не знає про React, `features` використовують `api` через хуки React Query, компоненти отримують дані з хуків.

## Ключові рішення

### Сесія і повтори (`src/api/httpClient.ts`)

- **401 → rotate → один повтор.** Rotate — це один спільний проміс (`rotateRequest ??= …`). Усі запити, які отримали 401, поки він виконується, чекають на нього ж. Після завершення проміс скидається.
- **Пізній 401.** Запит міг вийти ще до rotate, а 401 отримати вже після нього. Щоб не запускати другий rotate, клієнт веде лічильник `sessionGeneration`: якщо rotate уже завершився після старту запиту, запит просто повторюється.
- **Rotate не запускає rotate.** Auth-ендпоінти викликаються з `skipSessionRefresh`, а сам rotate іде повз 401-логіку.
- **Невдалий rotate або повторний 401** викликають `onSessionExpired`. `AuthProvider` на це очищує кеш React Query і стан, і `RequireAuth` перекидає на `/login`, зберігаючи поточний URL у `state.from`. Після повторного входу користувач повертається на ту саму сторінку з тими самими параметрами списку.
- **`device_session_token`** живе тільки всередині `authApi.signIn` (login → issue одразу). Він не потрапляє ні в стан, ні в storage, ні в URL.
- **fingerprint:** 16 випадкових байтів (`crypto.getRandomValues`) → 32 hex-символи. Генерується один раз і зберігається в `localStorage`; якщо storage недоступний, значення живе в пам'яті вкладки.
- **Токени сесії** клієнт не бачить: сесія зберігається в стані мока (аналог HttpOnly-cookie).
- **Вихід:** `revoke`, потім (навіть якщо revoke впав) `queryClient.clear()` і скидання стану.

### CSRF

- Перед першим API-запитом клієнт робить `GET /csrf`. Паралельні запити чекають на один і той самий запит токена.
- `X-CSRF-TOKEN` додається до POST/PUT, `X-Requested-With: XMLHttpRequest` — до всіх запитів. Мок відповідає 400, якщо цього заголовка немає.
- **419:** клієнт перезапитує токен і повторює запит не більше одного разу. Якщо кілька запитів одночасно отримали 419 з тим самим старим токеном, новий токен запитується один раз.

### Валідація відповідей (`src/api/schemas.ts`)

- Для кожної відповіді API є zod-схема. Типи `User`, `Webhook`, `WebhookList` виводяться з них через `z.infer`, тож схема і тип не можуть розійтися.
- `HttpClient` приймає `schema` в опціях запиту і повертає вже перевірені дані. Якщо відповідь не відповідає контракту, клієнт кидає `ApiError` з типом `InvalidResponse`, а не передає в UI дані неправильної форми.
- Тіло помилки (`{ error: { type, message, payload } }`) теж розбирається zod-схемою.
- Запити без тіла відповіді (`issue`, `rotate`, `revoke`) викликаються без схеми й повертають `void`.

### Список

- URL — єдине джерело істини для `page` і `search` (`useWebhookListParams`). Тому параметри відновлюються після перезавантаження і при навігації назад/вперед. Значення за замовчуванням (`page=1`, порожній пошук) в URL не пишуться.
- Зміна пошуку видаляє `page`, тобто повертає на першу сторінку. Введення debounce'иться (300 мс). Якщо URL змінюється ззовні (назад/вперед), поле пошуку синхронізується з ним.
- `placeholderData: keepPreviousData`: поки вантажиться нова сторінка, видно попередню (приглушену).
- Є стани завантаження, помилки (з кнопкою повтору), порожнього пошуку і сторінки поза діапазоном.

### Редагування

- Окрема сторінка `/webhooks/:id`. Query-рядок списку передається через `location.state`, тож «Скасувати», «Зберегти» і «До списку» повертають на ту саму сторінку з тим самим пошуком.
- Дві лінії валідації. Клієнтська zod-схема (`webhookFormSchema`, `loginSchema`) дає миттєвий відгук і не пускає очевидно некоректні дані на сервер (обов'язкова назва, HTTP/HTTPS-URL, `trim`). Сервер усе одно лишається джерелом істини: 422 `payload` розкладається по полях через `applyServerErrors`. Помилки для полів, яких немає у формі, і всі не-422 помилки показуються над кнопкою як загальна помилка форми.
- Серверну помилку біля поля найпростіше побачити на вході: коректний email і невірний пароль дають 422 на полі `password`.
- Після збереження: `setQueryData` для деталей і інвалідація списків.

### Мок (`src/mocks`)

- Один користувач, 27 вебхуків, стан у пам'яті. Сесія діє 30 с, rotate продовжує її на 30 с від поточного моменту. До `issue` і після `revoke` rotate повертає 400.
- Перевірки йдуть у порядку `X-Requested-With → CSRF (POST/PUT) → сесія → операція`. CSRF перевіряється до операції.
- `/auth/login` вимагає непорожній `X-Captcha-Token`. Клієнт передає заглушку `captcha-stub-token`, віджет капчі не підключено.
- Хендлери використовують `*/шлях`, тому той самий набір працює і в браузері, і в Node-тестах.

## Тести

`src/api/httpClient.test.ts` (Vitest + `msw/node`, справжні хендлери):

1. **Обов'язковий:** два паралельні запити отримують 401, виконується рівно один rotate, обидва повтори успішні, `onSessionExpired` не викликається. Щоб тест був детермінованим, rotate утримується, доки обидва запити не отримають 401 (хендлер-обгортка, яка потім передає запит справжньому хендлеру).
2. Невдалий rotate (після revoke) завершує сесію.
3. 419 → новий CSRF-токен → один повтор.
4. Відповідь, що не відповідає zod-схемі, відхиляється з `InvalidResponse`.

Перевірив, що перший тест справді ловить регресію: якщо замінити `??=` на `=` (rotate без спільного промісу), тест падає з `expected 2 to be 1`.

## Що свідомо не зроблено / можна покращити

- Схеми й типи API написані вручну за контрактом. Зі справжнім OpenAPI їх варто генерувати (наприклад `openapi-typescript` / orval + zod), щоб не підтримувати двічі.
- Немає UI-тестів (Testing Library). Покрито тільки транспортний шар, бо там найризикованіша логіка.
- Після перезавантаження сторінки потрібен повторний вхід: стан мока живе в пам'яті сторінки, що дозволено умовами. При старті застосунок все одно пробує `/v1/me`, тож зі справжньою HttpOnly-cookie сесія відновилася б без повторного входу.
- MSW потребує Service Worker. У браузерах або режимах, де SW заблоковано, мок не запуститься.
